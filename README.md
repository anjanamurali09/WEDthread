# WEDthread

A wedding-planning platform for multicultural and destination weddings. Couples plan events, guests,
RSVPs, seating, menus, budget and a registry, and publish a wedding website. Venues and vendors list
themselves in a marketplace that couples can browse and enquire with.

Live site: **https://www.wedthread.co**

## Getting started

Requirements: Node 20.19 or newer (or 22.12+), npm, and the [Supabase CLI](https://supabase.com/docs/guides/cli)
(only needed for edge functions and migrations).

```bash
git clone https://github.com/anjanamurali09/vowzy.git
cd vowzy
npm install
cp .env.example .env     # then fill in the values (ask the owner)
npm run dev              # http://localhost:8080
```

> **Warning: local development talks to the live database.** `.env` points at the production Supabase
> project, so anything you create, edit or delete locally is real. Be careful, or ask for a separate
> development project.

Useful commands:

| Command | What it does |
| --- | --- |
| `npm run dev` | Dev server on port 8080 |
| `npm run build` | Production build (the same command Cloudflare runs) |
| `npx tsc --noEmit` | Type check. Should print nothing |
| `npm run lint` | ESLint |

## Tech stack

- **TanStack Start** (React 19, server rendering) with **TanStack Router** (file-based routes) and **TanStack Query**
- **Tailwind CSS v4**, Radix UI primitives, lucide icons
- **Supabase**: Postgres with row-level security, auth, storage, edge functions (Deno)
- Built with **Vite** and **Nitro** into a **Cloudflare Worker** (`vite.config.ts`)
- PDF and Excel exports (jsPDF, ExcelJS), drag and drop (dnd-kit), charts (Recharts)

## Project layout

```
src/
  routes/            File-based routes. One file per page (see below)
    _authenticated/  Everything behind login (dashboard, guests, budget, admin, ...)
    w.$slug.tsx      Public wedding website; w.$slug_.registry.tsx is its registry
    v*.tsx, venue*   Public vendor and venue marketplace pages
    auth.*.tsx       Sign in, sign up, role picker, password reset
  components/        Shared UI. components/ui/ holds the base primitives
  lib/               Helpers: wedding-hooks.ts (data hooks), website-templates.ts, exports, currency...
  hooks/             React hooks (active role, saved feedback, ...)
  integrations/supabase/   Client and generated database types
  assets/            Bundled images and fonts
  routeTree.gen.ts   GENERATED by the router plugin. Do not edit by hand
supabase/
  migrations/        Database changes, in order (SQL)
  functions/         Edge functions (TypeScript on Deno)
  checks/            Read-only SQL for auditing the live database
  config.toml        Per-function settings (e.g. which functions skip JWT checks)
public/              Static files (favicon, template photos and artwork)
```

Routing notes (TanStack file conventions):
- `$slug` in a filename is a URL parameter.
- A trailing underscore (`w.$slug_.registry.tsx`) stops a route nesting inside its parent. Without it
  the registry would render inside the wedding website page.
- `_authenticated` is a layout that redirects signed-out visitors to `/auth`.

### Roles

A person can hold several roles: `couple`, `planner`, `venue`, `vendor`, `seller`, `admin`
(table `user_roles`). The active role decides the sidebar and the dashboard. Admins review vendors,
venues, claims and suggested edits under `/admin/*`.

A wedding can have **collaborators** (a second person with full edit access, matched by email).
Only the owning couple can invite them.

## Environment variables

Local `.env` (see `.env.example`):

```
SUPABASE_PROJECT_ID  SUPABASE_URL  SUPABASE_PUBLISHABLE_KEY
VITE_SUPABASE_PROJECT_ID  VITE_SUPABASE_URL  VITE_SUPABASE_PUBLISHABLE_KEY
```

The publishable key is public by design; row-level security is what protects the data.

**Cloudflare** (project `wedthread` → Settings):
- *Build variables* (must be set at build time): `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`,
  `VITE_SUPABASE_PROJECT_ID`, and `VITE_STRIPE_PUBLISHABLE_KEY` when payments are on.
- *Runtime variables*: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, and the **secret**
  `SUPABASE_SERVICE_ROLE_KEY`. `keep_vars` is set in `vite.config.ts` so deploys do not wipe dashboard values.

**Supabase** (Edge Functions → Secrets): `RESEND_API_KEY`, `RESEND_FROM_EMAIL`, `APP_URL`
(defaults to `https://www.wedthread.co`), `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`,
`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` (the last two only for the Google Sheets integration).

The service-role key bypasses all security rules. It must never appear in code, in git, or in a `VITE_` variable.

## Deploying

**The website.** Push to `main`. Cloudflare runs `npm run build` and deploys (about two minutes).
Check progress under Workers & Pages → `wedthread` → Deployments. There is no staging site, and every push
to `main` goes straight to production. Prefer a branch and pull request, and merge when it is ready.

**Edge functions are NOT deployed by a push.** Deploy each one you change:

```bash
supabase functions deploy <function-name> --project-ref pthcamxqautjjsppbfaj
```

**Database changes are NOT automatic either.** Migrations are plain SQL files in `supabase/migrations/`
(named `YYYYMMDDHHMMSS_description.sql`). They are run by hand in the Supabase SQL editor, in order.
Because nothing records which have been applied, run the read-only check after changes and compare:

- `supabase/checks/check_migrations.sql` lists tables and columns the migrations define that are missing from the live database
- `supabase/checks/audit_security.sql` lists what signed-out visitors can read or call, and which tables lack row-level security
- `supabase/checks/inventory_accounts.sql` lists accounts, weddings and businesses

Order matters when code and schema change together. Add the database change first when the new code depends on it;
for removals, deploy the code first and drop the old column afterwards.
Stage 2 of the business privacy change, `20261007150000_businesses_privacy_drop_vat_column.sql`,
runs only after the code that reads the VAT number from `business_private` is live. Check whether it has been run before assuming.

## Edge functions (`supabase/functions/`)

| Function | What it does |
| --- | --- |
| `send-collaborator-invite` | Owner-only. Invites a collaborator: Supabase invitation for new people, a branded email for existing accounts |
| `send-payment-reminders` | Emails couples reminders for expenses; run every 15 minutes by `pg_cron` (see `20261007110000_schedule_payment_reminders.sql`, which needs the project's public key filled in) |
| `submit-enquiry` | Couple sends an enquiry to a vendor or venue |
| `notify-viewing-request`, `notify-business-submission` | Emails owners and the admin; require a signed-in owner |
| `create-setup-intent`, `stripe-webhook` | Stripe card setup and webhooks (the webhook verifies Stripe's signature and has `verify_jwt = false` in `config.toml`) |
| `fetch-product-metadata` | Registry: reads a pasted product link. Signed-in only; refuses private and local addresses |
| `google-oauth`, `google-sheets-sync` | Optional Google Sheets two-way sync for guests and budget |

## Conventions

- **No floating popups.** Do not add toasts. Import `toast` from `@/lib/toast`: success calls do nothing,
  and errors show in a bar across the top of the page. For save buttons use the `useSavedFeedback` hook
  (the button itself changes colour and label), and show errors as inline text.
- **Everything the public can read goes through row-level security.** Each new table needs RLS enabled
  and explicit policies. Signed-out visitors (`anon`) have SELECT only on the tables listed in
  `20261007120000_tighten_anon_access.sql`; a new table is not public unless a migration grants it.
- The wedding website and its templates are driven by `src/lib/website-templates.ts` plus each wedding's
  `site_customization`; the public site and the editor preview share the same render code (`SiteShell`).
- **The logo is drawn, not typed.** `src/components/logo.tsx` renders fixed outlines (`logo-paths.ts`, generated from the Didot and Snell Roundhand letterforms) so it looks identical on every device. Do not replace it with text in those fonts: they exist only on Apple computers. The app's main fonts (Poppins and Newsreader) are self-hosted through `@fontsource` for the same reason.
- Images imported from `src/assets` are bundled and hashed. Do not reference remote or platform-specific asset paths.

## Security notes

- Row-level security is on for every table. Signed-out visitors can read only published wedding fields,
  public registries, approved venues and vendors, and similar listing data.
- The VAT/tax number of a business lives in `business_private` (owner and admin only).
- Edge functions that send email require a signed-in caller and check ownership.
- Turn on two-step login for GitHub, Cloudflare, Supabase and Resend.

## Known gaps

- No staging environment: local development and production share one database.
- Supabase's free plan has no automatic backups. Upgrade to Pro before real users rely on the data.
- Stripe is in test mode.
- The Google Sheets integration needs Google credentials before it works.
- The `Vendors/` and `Venues/` folders (raw listing photos) are kept out of git and exist only on the owner's computer.

## Handover checklist

When someone new joins, invite them (do not share passwords):

1. **GitHub**: repository → Settings → Collaborators
2. **Cloudflare**: account → Members (needs access to Workers & Pages and DNS for domain changes)
3. **Supabase**: organization → Team (needed for the database, functions and secrets)
4. **Resend**: team member, only if they will work on email
5. Give real environment values through a password manager, not through chat or email

Questions about how something is wired are usually answered by `src/lib/wedding-hooks.ts` (data access),
`src/routes/_authenticated/route.tsx` (login guard) and `supabase/migrations/` (the database, in order).
